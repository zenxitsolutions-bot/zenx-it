## Decisions made

- Fixed 30-minute call duration for everyone (a single constant), not a per-call/per-dietitian
  field — user-confirmed. Rules out variable-length sessions for now; simplifies overlap math to
  "any existing call within ±30 min of the requested start."
- One generalized `dietitian_availability_exceptions` table (`closed`/`open` + a datetime range)
  instead of separate tables for "blocked date" / "blocked time" / "holiday period" / "specific-date
  hours" — they're the same shape at different time spans. Rules out ever needing to reconcile two
  parallel "is this day off" mechanisms.
- Availability management is dietitian self-service only — user-confirmed. Rules out an
  admin-edits-another-dietitian's-hours path; if that's needed later it's new scope, not something
  silently half-built here.
- A dietitian/admin can pass `force: true` to bypass the rules when booking/rescheduling on
  someone's behalf (e.g. a genuine emergency); a client can never force, regardless of what they
  send — user-confirmed. Rules out clients ever bypassing the rules through the same field.
- No weekly-hours rows configured at all = unrestricted, not closed-all-week — mirrors the existing
  `must_change_password` precedent (a restrictive flag must never retroactively lock out an
  existing/seeded account). Rules out needing a seed-data migration for every existing dietitian.
- Tests use Node's built-in `node:test` (zero new dependencies) — user-confirmed, since no test
  framework existed anywhere in the repo before today.
- The pure/impure split (`availability.js` vs. `availabilityGuard.js`) exists specifically because
  the required test scenarios (outside hours, blocked date/time, overlap, back-to-back) needed to
  be fast and DB-free, while the concurrent-booking race genuinely needs a real database. Rules out
  a single service file that would force every test through a live MySQL connection.

## Problems hit & how they were solved

- **The concurrent-booking race test was genuinely flaky at first** (not a test artifact — a real
  bug). `EXPLAIN` on the guard's `SELECT ... FOR UPDATE` range query showed MySQL choosing the
  single-column `idx_calls_dietitian` index over a range scan, which next-key-locks every row for
  that dietitian regardless of `scheduled_at` — real lock contention between unrelated,
  non-overlapping bookings for the same dietitian, not just a missed optimization. Fixed by adding
  a `(dietitian_id, scheduled_at)` composite index and a `USE INDEX` hint in
  `lockOverlappingCalls`, verified via `EXPLAIN` showing `type: range` on the new index afterward.
- **Even with the tight index, two concurrent adjacent (back-to-back) bookings could still hit a
  genuine InnoDB deadlock** (`ER_LOCK_DEADLOCK`), reproduced directly via a standalone script:
  two transactions each hold a gap lock then try to insert, forming a real lock cycle that InnoDB
  detects and kills one side of. This is expected behavior for this row-locking strategy, not a
  logic bug — the standard mitigation is a transaction retry, so `withTransaction`
  (`server/src/db/pool.js`) now retries up to twice on `ER_LOCK_DEADLOCK`/`ER_LOCK_WAIT_TIMEOUT`.
  Reran the full integration suite 5× after each fix to confirm determinism, not just a single pass.
- **The new "Availability" tab rendered completely blank (no visible tab labels)** the first time it
  was opened in a real browser. Root cause: `client/src/components/ui/tabs.jsx` (a shadcn primitive
  installed early on but — checked via repo-wide grep — never actually used anywhere until this
  screen) used bare Tailwind boolean-attribute selectors (`data-horizontal:`, `data-active:`,
  `group-data-horizontal/tabs:`) that only match a literal empty `data-horizontal`/`data-active`
  attribute, but Radix's actual Tabs primitive sets *valued* attributes
  (`data-orientation="horizontal"`, `data-state="active"`) — so none of the selectors ever matched.
  This was a latent, pre-existing bug unrelated to anything specific to this feature; fixed by
  switching every occurrence to the bracketed value-matching form (`data-[orientation=horizontal]:`,
  `data-[state=active]:`), verified in a real browser afterward (tab strip renders, switching
  works).
- Native `<input type="time">`/`<input type="datetime-local">` fields didn't accept raw simulated
  keystrokes from the browser-automation tool during manual verification (a known automation-tool
  quirk with multi-segment native inputs, not an app bug) — worked around by setting values directly
  via the form-input tool instead of simulated typing.

Spec ask (section 1.5): client <-> assigned dietitian messaging. Persistent history both sides can
see in full; each conversation correctly scoped to its client/dietitian pair; server-side
enforcement on every endpoint so a user can never read or post to a conversation they aren't part
of. Include a conversation list for dietitians (multiple clients), an unread indicator, and
sensible ordering. Polling is fine — no websocket infrastructure.

### Done today

- **New `messages` table and API**, admin excluded entirely (`403` — not a party to any
  conversation). Conversation identity is the `(client_id, dietitian_id)` pair itself; no separate
  `conversations` row exists. `server/src/models/Message.js`, `schemas/message.schema.js`,
  `controllers/message.controller.js`, `routes/message.routes.js`, mounted at `/api/messages`.
  - **Server-side scoping, enforced in one place.** `message.controller.js#resolveConversation` is
    the single function every route calls to decide "what conversation, and is this caller
    actually in it": a client caller can never name who they're messaging — it's always derived
    from their own *current* `assignedDietitian` (`400` if none set, never trusted from the
    request); a dietitian must name a `client` and can only ever address one currently assigned to
    them (`assertDietitianOwnsClient`, the same helper `/progress`, `/plans`, and `/client-notes`
    already use — `403` otherwise). Read this as the direct answer to the spec's "enforce this
    server-side on every endpoint": there's exactly one place this can be gotten wrong, not five,
    and if a client is later reassigned to a different dietitian the old thread becomes
    inaccessible to both the old dietitian and the client's own lookup — scoped to the live
    relationship, not preserved as a point-in-time record (a deliberate call, documented in
    `schema.sql` and `docs/API.md`).
  - **Unread tracking** — one `read_at` column per message (not per-party: a 1:1 thread's message
    has exactly one possible reader, so a single timestamp is enough). `POST /messages/read` stamps
    every message in a conversation not sent by the caller; `GET /messages/unread-count` gives a
    single badge number (client: their one conversation; dietitian: total across every
    conversation); `GET /messages/conversations` gives the per-conversation breakdown.
  - **Dietitian conversation list** — `listConversationsForDietitian` (window-function "latest
    message per client" query, same `ROW_NUMBER() OVER (PARTITION BY ...)` pattern already used in
    `latestProgressByClientIds`) returns one row per *currently* assigned client, including ones
    with zero messages yet (so a dietitian can start a conversation), ordered most-recently-active
    first, then alphabetically for the rest — the "sensible ordering" the spec asked for.
- **Client UI** — `ClientMessagesScreen.jsx`: a single conversation via the new shared
