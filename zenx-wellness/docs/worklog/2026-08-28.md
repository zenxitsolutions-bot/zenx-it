### Decisions made

  `acme.com` far more often than `https://acme.com`, and an href without a scheme resolves as a

## Session 4

**Phase:** Bugfix — intermittent `ERR_CONNECTION_RESET` on login (both apps)
**Session time:** evening

### Done today

- Fixed intermittent `net::ERR_CONNECTION_RESET` on the login POST, reported against the ZenX admin
  portal and present identically here. Cause was transport-level, not application code — nothing
  was ever logged server-side, which is why it looked like a phantom.
- Node closes an idle keep-alive socket after **5s** (`server.keepAliveTimeout` default). Chrome
  holds pooled sockets much longer, and **will not silently retry a non-idempotent request** onto
  one it finds closed — it retries GETs, which is exactly why only the login POST ever showed this
  while the admin portal's 8s GET polling looked perfectly healthy. Sitting on a login form for
  more than 5s (i.e. always — you are typing) and then submitting races the POST onto a dead socket.
- Set `keepAliveTimeout = 65s` / `headersTimeout = 66s` on both servers, so the server's idle window
  is comfortably longer than the browser's rather than shorter.

### Files added / changed

| File | Change |
|---|---|
| server/server.js | `app.listen(...)` result captured; `keepAliveTimeout` / `headersTimeout` raised |
| ../zenx-applications/admin-server/server.js | same change (this is where it was reported) |

### Decisions made

- 65s/66s rather than disabling keep-alive — matches the conventional value used behind proxies with
  60s idle timeouts, and keeps connection reuse (the admin portal's polling depends on it).
  `headersTimeout` must stay above `keepAliveTimeout` or it pre-empts it.

### Problems hit & how they were solved

- Not reproducible by ordinary means: 120 sequential `curl` requests and ~2.5 minutes of live
  dashboard polling in Chrome were 100% clean, because each opens a fresh connection (curl) or is a
  retryable GET (polling). Reproduced instead with a raw `net.Socket` held open by hand across a
  measured idle gap, then reused with a POST — a clean boundary at Node's 5s default:

  | idle before reusing socket | result |
  |---|---|
  | 3s | `HTTP/1.1 401` — request went through |
  | 6s / 7s / 20s | socket dead / `ECONNRESET` |

  After the fix, 7s and 20s both return `401` on both servers.
- A `node --watch` restart destroys pooled sockets the same way, so a file save while the browser
  has the app open produces the identical error. Unavoidable in dev, but no longer the *only* way
  to hit it.

- [ ] Everything from Sessions 2 and 3 is still open.
- [ ] The admin portal issues a CORS preflight on **every** poll (no `Access-Control-Max-Age` on
      either server), doubling request count. Not a bug, but easy waste — worth setting `maxAge`

### Decisions made

- **Denial is uniform.** Unknown slug, wrong company, and user-with-no-company all return the same
  403 wording, so the login form cannot be used to enumerate which company slugs exist.
- **The tenant check runs after the password check**, so it is only reachable by someone who has
  already proved they own the account — a distinct error there reveals nothing.
- **`CompanySlugGuard` is explicitly not the boundary.** Documented in the file: it runs in the
  browser, where the user controls everything. The real isolation is that every controller derives
  the tenant from `req.user.companyId` on the verified token. The guard only makes the refusal
  visible.
- **Collection checks are bidirectional.** Each tenant holds a row named `"<slug> only"`, so the
  probe asserts the caller *sees its own* and *does not see the other's*. Asserting only absence
  would pass on an empty table and prove nothing.

- `createRecipe` takes no `companyId` — `listRecipes` scopes via the creating user's company

### Done today

- **The bare `/login` was a hole in the tenant rule, and it was my own doing.** Session 7 decided
  "`companySlug` is optional, so `/login` stays company-agnostic". That was wrong: every user
  belongs to exactly one company (`users.company_id` is required by `createUser`, and a check
  confirmed **0 rows** have it NULL), so a login that names no company simply skipped the slug
  comparison entirely. Reported against `test@gmail.com` (company `hello`), which could sign in at
  `/login` instead of `/hello/login`.
- `login` now refuses any request with no `companySlug`. There is no company-agnostic way in.
- The refusal is **actionable, not a dead end**: it returns the caller's own company login path in
  `details.companyLoginPath`, and the page renders it as a "Go to your company's login page" link.
  Safe to disclose — the line is only reachable after the correct password.
- `ApiError.forbidden` now accepts `details` (it already existed on `badRequest`).

### Decisions made

- **Refuse rather than redirect.** The alternative — authenticate at `/login` and bounce the user
  into their own tenant — would satisfy the letter of "no cross-tenant login" but leaves a second
  door into the app that the slug check never guards. One door per company is easier to reason
  about and to test.
- **Naming the company URL is post-password only.** A wrong password still returns the same 401 an
  unknown address would, so this cannot be used to test whether an email exists or to discover
  which company it belongs to. Covered by two explicit probe checks.

### Problems hit & how they were solved

- Wrote the fallback string through a Python heredoc as `'...company\\'s...'`, which reached the
  file as an unescaped `'` inside a single-quoted JS string. `node --watch` reported
  `SyntaxError: missing ) after argument list` and the server sat in "Failed running" — every probe
  request came back `000` until it was fixed. Switched to double quotes.
