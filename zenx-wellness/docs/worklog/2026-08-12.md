## Decisions made

- **Preserve the `_id`-shaped JSON contract exactly**, rather than switching the client to `id` —
  ruled out a client-side rename touching ~30 files for zero functional benefit; the client
  reads `_id`/`createdAt`/`tags`/`feedback` in ~15 files, confirmed by grep before deciding.
- **UUID (`VARCHAR(36)`) primary keys everywhere**, generated in app code, not `AUTO_INCREMENT` —
  keeps every foreign key a plain string comparison, matching `req.user.id` / `String(x)` checks
  already used throughout the controllers, and is what makes reusing Mongo's `_id.toString()`
  during migration safe (no id-remapping table needed). Two purely-internal join tables
  (`recipe_tags`, `plan_meals`) use `AUTO_INCREMENT` instead since their own id is never
  serialized to the client.
- **`plan_meals` gets an explicit `idx` column** — `updateMealStatus` and the client's
  `plan.meals.indexOf(meal)` both address a meal by array position, not by any id, so meals are
  always read back `ORDER BY idx`.
- **Pool-level `timezone: 'Z'`** — without it, `mysql2` would serialize JS `Date` params using the
  server host's local offset, which is exactly the class of bug this codebase already hit once
  (documented in `insights.controller.js`'s and `seed.js`'s own comments about a real
  UTC-vs-local `startOfWeek()` bug from 2026-08-11). Set once at the pool so it can't recur.

## Problems hit & how they were solved

- **Nested `meal.recipe` objects came back with `id` instead of `_id`.** `Plan.js` reused
  `Recipe.js`'s `mapRecipeRow` to build the populated `meals[].recipe` object, but that nested
  object never passes through a controller's own `toClientShape` call the way a top-level recipe
  does — only the plan's own top-level `id` gets renamed. Caught by an actual curl smoke test
  against a real seeded plan, not by reading the code (the exact same class of bug this project's
  worklog has flagged before: contract-shape bugs only show up against real data). Fixed by
  wrapping the nested recipe in `toClientShape` inside `Plan.js#getMealsForPlans`.
- **`COUNT(*)`/`GROUP BY` results risk coming back as strings from `mysql2`** depending on the
  BIGINT range, which would have silently broken `conversionRate`/`activeClients`/chart math in
  `insights.controller.js` (string concatenation instead of addition). Added explicit `Number()`
  casts in every model function returning an aggregate count, verified via curl that
  `admin-overview` returns real numbers.
- **Docker Desktop wasn't running** when first needed for the throwaway MySQL dev container —
  started it, waited for the daemon, then `dev-verify-mysql.mjs` worked as intended.
- **Claude-in-Chrome extension not connected** (same gap flagged in every prior worklog for this
  project) — couldn't do the planned real-browser login check for all three roles. Substituted an
  extensive curl-based smoke test instead: login (all 3 roles), recipes CRUD + tag replace, plan
  create/update-meals-wholesale/delete, meal-status-by-index PATCH, report create + feedback
  thread, calls, enquiries + pagination, both insights endpoints — all verified against the live
  MySQL-backed server with a clean server log (no errors, all 2xx/204). `npm run build` on the
  client also passes (client code is untouched by this migration).
