- **Bug found and fixed**, `client/src/api/axiosClient.js`: the 401 refresh-and-retry interceptor
  had no exclusion for `/auth/refresh` itself. A 401 from `/auth/refresh` (e.g. no cookie, which
  is the normal state for every first-time visitor) re-entered the same interceptor, which
  reused the *same* pending `refreshPromise` for its own retry — i.e. awaited a promise that
  could only resolve once itself resolved. Deadlock. Since `AuthProvider` calls `refreshRequest()`
  on every mount and `ProtectedRoute` renders `null` while `isLoading`, this meant `isLoading`
  would never flip to `false` for an anonymous visitor and `/portal` access would silently
  never load, even after a later successful login. Confirmed the hang directly: ran the original
  logic against the live server with no cookie under a 5s timeout — zero output, confirming it
  never settled. Fixed by excluding `/auth/refresh`, `/auth/login`, `/auth/register` from the
  retry-on-401 path (login/register 401s are real credential/validation failures, not stale
  tokens, so retrying them is also just wasted work). Re-ran the same test post-fix: rejects in
  27ms with the correct 401.
- Also fixed `RoleRoute.jsx` (crashed on `user.role` if `user` were ever null — added a guard and
  a real redirect target via a new `role → portal home` lookup) and `ProtectedRoute.jsx` (now
  passes `state={{ from: location }}` so the login/register pages can send the user back to
  where they were headed instead of always dropping them at the portal root).
- `client/src/lib/portalHome.js` — `getPortalHome(role)`. All three roles currently land on
  `/portal/overview` (that page already renders role-specific content itself), but this is a
  lookup, not a hardcoded literal, so a future phase can give a role its own distinct landing
  route without touching every redirect call site.
- `client/src/lib/authError.js` — `getAuthErrorMessage(error)` maps an axios error to one of:
  network-down (`!error.response`), `401` invalid credentials, `409` email already registered,
  `400` validation, or a generic fallback. **Deliberately did not** split "wrong password" from
  "unknown email" into separate messages — the backend intentionally returns the same generic
  401 for both (`server/src/controllers/auth.controller.js`) to avoid leaking which emails are
  registered (user-enumeration). Read the task's "wrong password, unknown email, network down"
  requirement as "distinguish the categories a user can hit," not as a request to add an
  enumeration vector — network-down, invalid-credentials, and email-taken are the three that are
  actually safe and useful to tell apart.
- `client/src/components/auth/AuthLayout.jsx` — shared split layout (form on cream, brand/quote
  panel on forest with soft blob shapes and lucide icons, not emoji) used by both `LoginPage` and
  the new `RegisterPage`. Breakpoint is `min-[1050px]:` to match CLAUDE.md §8's stated legacy
  breakpoint (checked `legacy/styles.css` — its actual `@media` breakpoints are 850px/600px, not
  1050px/650px, so CLAUDE.md's number and the legacy file disagree; followed CLAUDE.md's stated
  number since it's the standing instruction).
- Rewrote `LoginPage.jsx` and added `RegisterPage.jsx` (`client/src/routes/router.jsx` now has
  `/register`): shadcn `Form`/`FormField` (the hand-rolled composition from Phase 3) + RHF + zod,

  `getAuthErrorMessage`. Register collects name/email/password/confirm-password (confirm is

### Decisions made
- Bar charts (not line/area) for `growthSeries`/`dietitianWorkload`/`statusBreakdown` — the
  `dataviz` skill's form heuristic treats discrete counts over time buckets or categories as
  magnitude comparisons, not a continuous trend (that was `WeightTrendChart`'s job in Phase 6);
  single sequential hue throughout since each chart is one series and doesn't need a legend.
- `statusBreakdown` uses one hue ordered by pipeline stage rather than a multi-hue categorical
  palette — the five stages have an inherent order (new → closed), which reads more honestly as
  an ordered progression than as unordered category identity.

  sage-deep eyebrows) — unlike `text-muted`, these use CLAUDE.md §4's colors exactly as specified;
  fixing them would be a design deviation, not a bug fix, and CLAUDE.md is explicit that this is
  "a port, not a redesign." Flagged in `docs/PROGRESS.md` for the brand owner to decide.
- Didn't chase the vendor JS chunk (697KB) further after route-level splitting — that's React +
  React Router + TanStack Query + Radix + axios + zod + react-hook-form, needed on every route
  and cached after first load; manually splitting it further risked breaking the build for a
  metric that was already at target, for a goal ("route-level code splitting") that was already
  satisfied by the per-page chunks.
