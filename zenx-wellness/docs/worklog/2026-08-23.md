## Session 1

Spec ask (`docs/specs/2026-round2-fixes.md` item 7, pasted in chat — the file didn't exist yet,
recreated from the chat text): a dietitian sets 9:00 AM-5:00 PM working hours, but clients see
slots like 4:00 AM-11:30 AM (~5 hour shift). Diagnose end-to-end first, then fix with one
consistent timezone rule and write tests.

### Diagnosis (done before any fix, per the explicit ask)

Traced one slot end to end:

- **Storage**: `dietitian_weekly_hours.start_time`/`end_time` are plain MySQL `TIME` columns —
  mysql2 returns them as bare `'HH:MM:SS'` strings with **no date or timezone context at all**.
  The dietitian types e.g. "09:00" into a native `<input type="time">`
  (`WeeklyHoursForm.jsx`) and it's sent to the server and stored completely unmodified — no
  conversion happens anywhere on write. (Exceptions/blocked-time rows, by contrast, already store
  real UTC instants — `<input type="datetime-local">`'s value is genuinely local wall-clock, and
  `new Date(value).toISOString()` in `AvailabilityExceptionFormDialog.jsx` correctly converts
  browser-local → UTC before sending. Exceptions were never part of this bug.)
- **The actual bug — on read/compare**: `server/src/services/availability.js#checkAvailability`
  determined a candidate slot's "minutes since midnight" via
  `date.getUTCHours() * 60 + date.getUTCMinutes()` and compared that directly against the raw
  `startTime`/`endTime` strings parsed as plain numbers. In other words: the code silently
  **treated the dietitian's local wall-clock string as if it were already a UTC time-of-day** —
  not a double conversion, a *missing* one. There is no manual offset arithmetic anywhere
  (grepped for `getTimezoneOffset`, `5.5`/`330`, and any `new Date("09:00")`-style bare-time
  parsing — none exist) — this was a single, consistent misinterpretation at one comparison site,
  not an offset bug compounding across multiple places.
- **On render**: `SlotPicker.jsx`'s `formatTime(slot)` (`new Date(value).toLocaleTimeString(...)`)
  already correctly converts a real UTC instant to the *browser's* local time for display — this
  side was never wrong. It's precisely because the render side correctly converts UTC→local, and
  the write/compare side never converted local→UTC in the first place, that the net visible effect
  was "shifted by the dietitian's own UTC offset": a dietitian in a UTC-5 zone entering 9:00-17:00
  got compared as 09:00-17:00 UTC (not 14:00-22:00 UTC, the real intent); a same-timezone client
  then saw that returned UTC window converted back to their own UTC-5 local time — 04:00-12:00,
  i.e. displayed slots start at 4:00 AM with the last 30-minute slot at 11:30 AM. Exactly the
  reported symptom, reproduced deterministically in the new regression test using `America/Bogota`
  (fixed UTC-5, no DST) rather than relying on wherever this session happened to run.
- Neither the database driver nor the browser was doing anything wrong on their own — `mysql2` is
  configured `timezone: 'Z'` (treats every `DATETIME`/`TIMESTAMP` as UTC consistently, confirmed
  in `db/pool.js`) and correctly leaves `TIME` columns as bare strings; the browser's
  `toLocaleTimeString` correctly converts a real instant to local time. The bug was entirely in
  application code, in one function, in one branch.

### Fix — one consistent rule

Implemented exactly the rule specified:
- **Working hours are wall-clock in the dietitian's own IANA timezone.** New `users.timezone`
  column (`VARCHAR(64) NOT NULL DEFAULT 'UTC'`), settable via `PATCH /users/me`. Default `'UTC'`
  specifically because UTC-as-local was the old (buggy) behavior — every existing dietitian keeps
  byte-identical behavior until they explicitly set their real zone, so shipping this column can
  never silently relocate anyone.
- **Appointments/exceptions stay UTC instants** — already true, untouched.
- **Convert exactly once**, at the one place a candidate instant needs to become "what wall-clock
  time/weekday is this for the dietitian" — via `date-fns-tz` (`toZonedTime`/`fromZonedTime`), a
  real IANA-tz-database-backed library, newly added since the project had no date library at all.
  No manual offset math anywhere (no `+5.5`, no `getTimezoneOffset`).
- **Timezone labelled in the UI** — `SlotPicker.jsx` now shows "Times shown in your timezone
  (America/New_York, GMT-05:00)" (or whichever zone the viewer's browser reports) below the slot
  grid, via a new `client/src/lib/timezone.js` (plain `Intl`, no library needed client-side — an
  instant-to-local-time conversion for *display* is a solved problem in native JS; the missing
  piece was always the local-to-UTC conversion on the write/compare side, server-side).

**Mechanics of the fix** (`server/src/services/availability.js`):
- `checkAvailability` gained a `timezone` param (default `'UTC'`). The weekly-hours branch now
  computes the candidate's local minutes-and-weekday via `toZonedTime(candidate,
  timezone)` instead of `getUTCHours()`/`getUTCDay()`.
- `listAvailableSlots`'s `date` parameter now means the dietitian's **local** calendar date, not a
  UTC one — its day-start/day-end bounds are resolved via `fromZonedTime` rather than a hardcoded
  `+24h`, so a DST-transition day (23 or 25 real UTC hours) isn't silently truncated or padded.
- `availabilityGuard.js` fetches the dietitian's `timezone` (via `findUserById`, now accepting an
  optional `conn` for transaction consistency, matching the rest of this codebase's model
  functions) and threads it into both `assertSlotAvailable` (the booking check) and
  `getAvailableSlotsForDay` (the display query) — the exact same `timezone` value governs what
  gets shown and what actually gets accepted, so "shown as available" can never drift from
  "bookable" the way the original bug made possible.
- New `TimezoneField.jsx` on the dietitian's Availability screen (`AvailabilityScreen.jsx`, above
  Weekly hours) — a plain `<input list>` + `<datalist>` populated from `Intl.supportedValuesOf
  ('timeZone')` (the full, always-current IANA list — no bundled timezone-name library needed),
  pre-filled with the browser's own detected zone only when nothing's been saved yet, still
  requiring an explicit Save.

### Decisions made

- `date-fns-tz` added server-side only, not client-side — converting a UTC instant to a viewer's
  local time for *display* is already correctly solved by native `Intl`/`toLocaleTimeString` (that
  side was never broken); the only place that genuinely needed real IANA-tz-database logic was the
  server's local-wall-clock-to-UTC-instant comparison, so that's the only place gaining a
  dependency.
- `date` in `GET /calls/available-slots` now means the dietitian's local calendar date rather than
  a UTC one. This is a real, deliberate semantic change (flagged here rather than silently): a
  client's date picker still submits whatever `'YYYY-MM-DD'` string it has (computed from the
  viewer's own browser "today," unchanged), and for a client several hours removed from the
  dietitian, the exact calendar-day boundary between "today" and "tomorrow" can differ by one day
  between the two — a known, pre-existing class of scheduling-UX edge case (shared by most simple
  booking tools), not solved here. What the spec's actual tests require — correct time-of-day
  conversion and labelling — is fully solved; a full "which day bucket" UX redesign was out of
  scope for a bug-fix pass and wasn't asked for.
- `users.timezone` defaults to `'UTC'`, not auto-detected/backfilled from anywhere — deliberately
  requires each dietitian to explicitly set their real zone once, so no one is silently relocated
  by a migration. The new `TimezoneField` pre-fills the *input* with the browser's detected zone
  as a convenience, but still requires an explicit Save.
- Used fixed-offset, non-DST IANA zones (`America/Bogota` UTC-5, `Asia/Kolkata` UTC+5:30,
  `Asia/Tokyo` UTC+9) in the new tests rather than a DST-observing zone like `America/New_York` —
  fully deterministic regardless of what date the suite runs on, avoiding a test that would
  silently start failing (or passing for the wrong reason) twice a year.

### Problems hit & how they were solved

- `findUserById` didn't accept a connection param, but `availabilityGuard.js#assertSlotAvailable`
  needed to read the dietitian's timezone from inside an existing transaction. Rather than leave

  concurrently mutates `timezone`, but inconsistent with every other model function this codebase
  already threads a transaction connection through), extended `findUserById(id, conn = pool)` to
  match the established pattern (`Call.js#findCallById`, etc.).
- No local MySQL was reachable this session (confirmed via `npm run db:migrate` conceptually not
  run — no live DB to run it against — and starting `server.js` directly, which reached the

### Found and fixed anyway

Comparing `CallFormDialog.jsx` against `DietitianCallFormDialog.jsx` line-for-line surfaced one
genuine bug, distinct from the reported symptom:

- **Wrong dietitian source for the reschedule slot picker.** `CallFormDialog.jsx` passed
  `dietitianId={user.assignedDietitian}` (the client's *current* assignment) to `SlotPicker` in
  both book and reschedule mode. For booking a new call that's correct (there's no existing
  dietitian to defer to). For **rescheduling**, it's wrong: an existing call's `dietitian` is fixed
  at booking time and never changes, but a client's `assignedDietitian` can — if a client is later
  reassigned to a different dietitian, rescheduling an old call would show the *new* dietitian's
  availability while the server (`call.controller.js#updateCall`, which correctly uses
  `call.dietitian`, not the client's current assignment) validates against the *actual* owning
  dietitian — a real mismatch that could surface as a confusing rejection at save time. Didn't
  manifest in the live reproduction above only because the test client's assignment happened to
  match the call's own dietitian. Fixed: reschedule mode now passes `call?.dietitian?._id ??
  call?.dietitian`; book mode is unchanged (`user.assignedDietitian`, matching how
  `call.controller.js#createCall` itself derives it for a client caller).
- **A real crash-prone edge case in the shared `SlotPicker`.** `useAvailableSlots`'s query is
  `enabled: Boolean(dietitianId && date)` — whenever `dietitianId` is falsy, the query never runs,
  so `data` stays `undefined` forever while `isLoading`/`isError` both stay `false`. The render
  logic's next branch, `data.slots.length === 0`, would then throw a `TypeError` reading `slots` off
  `undefined` — a hard crash, not a graceful empty state, and exactly the kind of thing that could
  look like "the dialog does nothing" from the outside if a caller ever reaches this state (not
  currently reachable in the flows above given the previous fix, but a latent landmine in a shared
  component two different screens render into). Fixed: an explicit `!dietitianId` branch now
  surfaces "Couldn't determine who this call is with — please try again." instead of crashing.
- Audited every other mutation call site in the client calls surface
  (`CallCard.jsx`'s cancel, `CallFormDialog.jsx`'s book/reschedule) — all already had `onError`
  toasts; nothing else swallowed. `NextCallCard.jsx` (Overview's next-call summary) has no
  mutations, nothing to audit there.

## Session 3

**Session time:** 2026-08-23 (same day, continued)

Spec ask (`docs/specs/2026-round2-fixes.md` item 1, pasted in chat and appended to that file):
moving an enquiry to Follow-up currently auto-creates a client account — too early. Follow-up
should book a call directly against the enquiry (no account); only marking an enquiry
"Successfully Converted / Won" should create the account, prefilled from the enquiry, carrying
over history/notes/calls so the new client isn't a blank slate. Also: audit and report (not
delete) any accounts the old behavior already created.

### What changed and why

The old flow: `PATCH /enquiries/:id { status: 'follow-up' }` called `ensureConvertedAccount` before
booking the call — the first time *either* Follow-up or Converted was reached, a real `users` row
was force-created, `mustChangePassword: true`, with `assignedDietitian` set to whoever was picked
for the follow-up. That's the exact behavior the spec calls "too early": a lead who's only had one
scheduled call already has a full client account and login, before anyone's actually decided
they're converting.

**New rule, one line: only `status: 'converted'` ever creates an account.** Follow-up now only
ever books a call — held against the enquiry itself, not a client.

- **Schema**: `calls.client_id` widened to `NULL`-able; new `calls.enquiry_id VARCHAR(36) NULL`
  with its own FK (`ON DELETE CASCADE` — deleting an enquiry before conversion also removes its
  unclaimed follow-up calls) and a `CHECK ((client_id IS NULL) <> (enquiry_id IS NULL))` — enforced
  at the DB level, not just in application code, that a call is with exactly one of a real client
  or a lead, never both, never neither, and never a stringified fake id standing in for one (the
  spec's explicit "handle this cleanly" ask).
- **`Call.js`**: `mapCall` now returns `call.enquiry = {_id, name, phone, email}` (same shape a
  populated `call.client` would have) whenever there's no client yet, so display code can do
  `call.client ?? call.enquiry` without caring which one it actually got. Every query that used to
  `JOIN users cu ON cu.id = c.client_id` (which would have silently excluded every enquiry-linked
  row) is now a `LEFT JOIN`, paired with a new `LEFT JOIN enquiries`. `createCall` accepts `client`
  *or* `enquiry` and throws if given both or neither (an application-level version of the same rule
  the new `CHECK` constraint enforces at the DB). New `reassignEnquiryCallsToClient(enquiryId,
  clientId, conn)` — an `UPDATE`, not a copy, so a call's own id/reschedule-history survives the
  hand-off from enquiry-scoped to client-scoped unchanged.
- **`enquiry.controller.js`**: `updateEnquiry`'s `'follow-up'` branch now only books the call
  (`createCall({ enquiry: existing.id, ... })`) — no account, no `planId`/`planDuration`/`password`
  needed or accepted anymore (removed from `updateEnquirySchema`'s `follow-up` variant). The
  `'converted'` branch is now the sole account-creation path, and — new — runs the *entire*
  conversion (account creation, re-pointing any enquiry-linked calls, copying history into notes,
  and the status/history update itself) inside **one transaction**: either the whole thing commits
  together or none of it does, so there's no partial state to detect or recover from on a retry
  (unlike the old flow's account-creation-outside-a-transaction design, which needed the
  persist-`convertedUserId`-immediately workaround for exactly that reason — not needed here since
  reassignment/note-copying don't have an external failure mode like a `409` availability conflict
  to guard against). Every `enquiry_history` row gets copied into one `client_notes` entry each
  (`[<Status label>] <note>`), giving the new client's profile a real trail instead of starting
  empty. Needed `conn` support added to `User.js#createUser`, `Enquiry.js#updateEnquiryById`,
  `EnquiryHistory.js#listByEnquiryId`, and `ClientNote.js#createClientNote` (all previously
  pool-only) to make this one-transaction design possible — matches the existing `conn = pool`
  pattern already used throughout the model layer.
- **Client**: `EnquiryFollowUpDialog.jsx` rewritten — no more plan/duration/password fields or
  `needsAccount` branching, just dietitian + slot + note. `EnquiryConvertedDialog.jsx`'s copy
  updated to describe the carry-over. `STATUS_LABEL.converted` relabeled "Successfully Converted /
  Won" (spec's exact wording) — the underlying `'converted'` enum value is unchanged, so this was a
  label-only change, not a new pipeline column. `DietitianCallCard.jsx` and
  `DietitianOverviewScreen.jsx`'s today's-calls list both now fall back to `call.enquiry?.name` (plus
  a small "Lead" badge and the enquiry's phone/email on the full card) instead of showing a
  generic "Client" placeholder for a not-yet-converted follow-up call.

### The two things I was explicitly asked to explain

**Email as login identifier, and what happens when it changes:** I read `server/src/utils/jwt.js`
and `authenticate.js` to check this rather than assume it. Both the access and refresh tokens sign
only `{sub: user.id, ...}` — the user's numeric/UUID id, never their email — and every
authenticated request looks the caller up by that id (`authenticate.js`, `findUserById(payload.sub)`).
`login()` is the *only* place `users.email` is ever read to identify an account, and that only
happens at the moment of login itself. **Conclusion: changing a user's email never invalidates
their current session.** Someone mid-session when their email is changed stays logged in exactly
as before; only the credential they'll need to type at their *next* login changes. No token
rotation, no forced re-login, and no extra code was needed to "handle" this — it falls out of the
token design already in place. The only thing that does need handling, and is handled, is
uniqueness: both `POST /users` and `PATCH /users/:id` reject a duplicate email with a `409`, shown
as a field-level error on the Email input, not a generic toast.

**Deactivating a dietitian and their upcoming appointments — what currently happens:** nothing.
Before this task there was no status concept on a user at all, so I checked directly rather than
assume: no existing code path touches `calls`, `assigned_dietitian_id`, or `plans` based on
anything. I deliberately designed `accountStatus` the same way — neither `inactive` nor
`suspended` cascades into or filters those tables. `suspended` only blocks login (both routes,
above); `inactive` doesn't even do that. So: **deactivating or suspending a dietitian cannot
silently orphan their upcoming appointments, because nothing about their appointments changes at
all** — they stay exactly as scheduled, still visible to the client, still visible to any other
admin/dietitian who could see them before. **The flag, honestly:** the flip side of "nothing
changes" is that a suspended dietitian's calls keep showing normally on their client's Calls tab as
if nothing happened (there's no "this dietitian is currently unavailable" indicator anywhere for a
client), and — separately — a suspended/inactive dietitian is *not* filtered out of the
dietitian-picker (`GET /users?role=dietitian`) a new or reassigning client uses, so a client could
still pick one. I deliberately didn't fix the picker-filtering half this session: that endpoint is

**Session time:** 2026-08-23 (same day, continued)

Spec ask (`docs/specs/2026-round2-fixes.md` item 6, pasted in chat and appended to that file):
uploaded client documents fail to load or preview in the dietitian portal's Report Review section.
Diagnose first, in a specific order (file URL/reachability, auth on the file request, CORS/CSP,
Content-Type, Content-Disposition, blob/objectURL handling), report the cause, then fix it: inline
preview for PDFs/images, a clear message for unsupported types, an always-present Download original
button, explicit loading/error states, and — explicitly flagged as something to verify and fix if
broken — server-side permission checking on the file route itself.

### Diagnosis (done before any fix, per the explicit ask, in the order given)

- **Is the file URL correct/reachable, and do uploads land where the reader looks?** Checked both
  path computations directly rather than assuming: `upload.js`'s multer `destination`
  (`server/uploads`, resolved from `server/src/middleware/upload.js`) and the old static mount's
  base in `app.js` (`server/uploads`, resolved from `server/src/app.js`) resolved to the exact same
  directory — not a divergent-base bug. **Not the cause.**
- **Auth on the file request.** This is where the real bug was: `app.js` served every uploaded file
  through `app.use('/uploads', express.static(uploadsDir))` — mounted before any auth middleware,
  outside `/api` entirely, with **no authentication and no ownership check of any kind**. Anyone
  who obtained or guessed a file's URL could fetch any client's uploaded medical report, logged in
  or not. **Confirmed cause of the "verify this" ask** — fixed (see below).
- **CORS or CSP blocking the iframe/embed.** Checked precisely rather than lumping "CORS/CSP" into
  one guess: `cors({ origin: env.clientOrigin, credentials: true })` is mounted before every route
  including the old `/uploads` static one, so actual CORS headers were already correct — not the
  cause. Content-Security-Policy is enforced against the page that *declares* it; the client is a
  Netlify-hosted static SPA with no CSP of its own (checked `index.html`/`netlify.toml` — neither
  sets one), so the *server's* helmet-set CSP (governing the server's own responses) was never
  actually capable of blocking anything the client page loads — also not the cause, and worth
  stating precisely rather than leaving "CSP" as a vague suspect. What **is** a real, confirmed
  cause is a related-but-distinct browser mechanism the checklist's "CORS or CSP" phrasing didn't
  name directly: **`Cross-Origin-Resource-Policy` (CORP)**, which `helmet()` sets to `same-origin`
  by default on every response from this server. Client and server are deployed to different
  origins in production (Netlify vs. Render) — the browser enforces CORP on cross-origin resource
  loads (images, iframes, and even authenticated `fetch()`/XHR requests, independent of and *in
  addition to* whatever CORS allows), so any viewer built against the old direct URL would have
  been silently blocked by the browser in production specifically, while probably working fine in
  local dev (same origin, no CORP restriction to violate) — a plausible reason this could have
  looked "broken in prod, fine locally" if anyone had tried building one before. **Confirmed real
  cause**, fixed by explicitly overriding CORP to `cross-origin` on the new file route only, not
  app-wide.
- **Content-Type / Content-Disposition.** Checked directly: `express.static` (and `res.sendFile`,
  which replaced it) infer `Content-Type` from the file's extension via `send`'s built-in mime
  table, and neither ever set `Content-Disposition: attachment` — only `res.download()` does that,
  which nothing in this codebase called. **Not the cause** — correctly not broken, confirmed by
  reading the actual code path rather than assumed from the framework's usual defaults.
- **Blob/objectURL handling, and early revocation.** N/A as a *cause*, because there was nothing to
  find here: **no viewer existed on either portal at all.** `DietitianReportCard.jsx` and the
  client's own `ReportCard.jsx` both rendered `report.fileName` as plain, unlinked text — no
  `<a>`, no `<img>`, no `<iframe>`, no fetch of the file, anywhere in the client. `seed.js` even has
  a comment ("reports uploaded for real through the UI will have a working download link") implying
  this was intended but never actually built. **The honest root cause, stated plainly**: the
  reported symptom isn't a broken viewer — it's that Report Review never had one, sitting on top of
  the two real bugs above that would have broken any viewer built the naive way (a direct URL) once
  one was added. This diagnosis is reported straight, matching the pattern from Session 2's
  "diagnose first" investigation earlier today — not papering over the gap with a vague "it works
  now."

### The fix

**Closed the unauthenticated file route.** Removed the `/uploads` static mount from `app.js`
entirely. Every file now goes through a new, permission-checked `GET /api/reports/:id/file`
(`report.controller.js#getReportFile`), sitting behind the same `authenticate`/
`blockIfMustChangePassword` stack the rest of `/api/reports` already uses, with the exact same
per-role ownership rule `listReports` already enforces: a client only their own report, a
dietitian only a report belonging to one of their own currently-assigned clients (via the existing
`assertDietitianOwnsClient` helper), admin any. `404` if the report doesn't exist *or* if the file
is missing from disk (caught via `res.sendFile`'s own `ENOENT` callback, not a separate
`fs.existsSync` check, avoiding a check-then-use race) — this exercises cleanly against the seeded
demo report, whose `filePath` deliberately doesn't point at a real file (see the `seed.js`
comment), giving a real, honest "file could not be found" error state to verify against rather than
a synthetic one.

**Fixed the CORP block.** The new route explicitly sets `Cross-Origin-Resource-Policy: cross-origin`
on its own response — scoped to just this route, not weakening helmet's stricter app-wide default
anywhere else.

**Built the actual viewer** (new shared `client/src/components/portal/shared/ReportFileViewer.jsx`,
used by both `DietitianReportCard.jsx` and the client's `ReportCard.jsx` — a report's filename is
now a button that opens it): fetches the file as an authenticated blob (`axiosClient`,
`responseType: 'blob'`, so the Bearer token/refresh-on-401 interceptor already in place just works —
never a bare `<img src>`/`<iframe src>` pointing at the API directly, which would both leak the file
to anyone who found the URL again and hit the same CORP wall). PDFs render in an `<iframe>`, images
in an `<img>`, both against a `blob:` object URL created from the fetched bytes; anything else shows
a clear "preview isn't available for this file type" message instead of a blank frame. **Download
original** is always offered, for every type, using the already-fetched blob (a temporary `<a
download>` against the same `blob:` URL — reliable regardless of cross-origin headers, since
`blob:` is always same-origin to the page that created it, unlike a direct link to the API). Loading
shows a skeleton; the error state surfaces the server's actual reason (not found / forbidden /
session expired) rather than a generic message — `getReportFileRequest` in `reports.api.js` had to
specifically handle the fact that with `responseType: 'blob'`, an error response's JSON body also
arrives as a `Blob`, not parsed JSON, so it's read back out and `JSON.parse`d to recover the real
server message.

**Object URL lifecycle** (the last checklist item): the viewer creates a fresh `blob:` URL exactly
when a new blob arrives (`useEffect` keyed on the blob) and revokes the previous one only in that
same effect's cleanup — never revoked while still referenced by the `<iframe>`/`<img>` on screen,
and never leaked past the component's lifetime either. The underlying React Query cache entry also
uses `gcTime: 0` so a closed viewer doesn't keep a (potentially large) file's bytes cached
indefinitely in memory.

**Adjacent fix, found while touching the same code**: `upload.js`'s multer `filename` callback used
the client-supplied `file.originalname` directly, unsanitized — multer does not strip path
separators from it itself, so an upload with an `originalname` containing `../` could have written
outside `server/uploads` (a path-traversal write). Not the literal bug reported, but the exact same
file-naming code path the read-side fix above depends on for safety, so fixed alongside it rather
than left as a landmine right next to code just hardened for the read side: `filename` now runs
`path.basename(file.originalname)` first. The new read-side `getReportFile` also defensively
`path.basename`s `report.filePath` before joining it to `uploadsDir`, so a read can never escape
the uploads directory even for any pre-existing row from before this fix.
