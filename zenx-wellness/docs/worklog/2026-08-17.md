## Decisions made

- Reused the existing `GET /users?role=` endpoint for the client-facing dietitian directory
  instead of adding a new route — the controller forces `role=dietitian` server-side whenever the
  caller is a client, so the same endpoint safely serves three very different scopes (admin: all
  users, dietitian: own clients, client: dietitian directory). Keeps the API surface small; ruled
  out a separate `/dietitians` route as unnecessary duplication.
  — Why: the endpoint already had role-based scoping (dietitian → own clients); extending the same
    pattern for `client` role kept the authorization model in one place instead of two.
- `assignedDietitian` is validated against a real `role:dietitian` row on every write path
  (`updateMe`, `createUser`, admin `updateUser`), not just checked for a non-empty string.
  — Why: the `assigned_dietitian_id` foreign key only requires the id to exist in `users`, not
    that it has `role:dietitian` — without app-level validation a client could self-assign another
    client's or an admin's id and silently break dietitian-scoped queries (plans/calls/reports)
    downstream. Confirmed by reading `plan.controller.js`'s `scopeToOwner`/`assertDietitianOwnsClient`,
    which trust `assignedDietitian` without re-checking the target's role.
  — What it rules out: a lighter schema-only check (`z.string().min(1)`) would have been
    insufficient since zod can't reach the database.
- Kept "Clients" (`/app/clients`, existing) and "Manage users" (`/app/users`, new) as two separate
  admin screens rather than merging them. `/app/clients` is the day-to-day "who am I taking care
  of" view shared with the dietitian role (same component); `/app/users` is the account-admin
  surface (create/role-change/reassign) admin needs and dietitian must never see.
  — Why: merging would have meant either giving dietitians create/role-change UI (a privilege
    escalation surface, since the backend correctly forbids it) or forking `ClientsScreen` per
    role, which is more churn than a second small screen.

### Problems hit & how they were solved

- Claude-in-Chrome still not connected → same `playwright-core` + system Chrome fallback as
  2026-08-11, re-derived from scratch since no reusable script was kept from that session.
- Several `page.locator('a[href="..."]')` calls hit Playwright's strict-mode "resolved to 2
  elements" error, because sidebar nav links and in-card "View all →" links share the same `href`.
  Fixed by scoping to `nav a[href="..."]` (the sidebar is the only `<nav>` in the DOM at rest; the
  mobile drawer's duplicate `Sidebar` is Radix-unmounted while closed).
  — Not an app bug, a test-script bug — noted here since it burned real time.
  → **Why this exists**: `Sidebar` intentionally shares one `href` between the persistent nav item
  and any inline shortcut link, so Playwright automation must scope to `nav`. A real user never hits
  this ambiguity — it's an artifact of `getByRole`/`locator` seeing both anchors, not a UX issue.
- Several early "issues" (a "choose a dietitian" prompt / dashboard heading not found immediately
  after `waitForLoadState('networkidle')`) turned out to be a Playwright networkidle-vs-lazy-chunk
  race specific to Vite's dev server (`React.lazy` route chunks fetch as a *second* wave of network
  requests slightly after the initial idle window closes) — not a real bug. Confirmed by re-running
  the same flow with an explicit `getByRole('heading', ...).waitFor()` instead of relying on
  `networkidle`, which passed cleanly and produced correct screenshots every time. Worth remembering
  for any future browser-automation session against this dev server: prefer waiting for a specific
  element over `networkidle` after a client-side route change.
- 401s on `POST /api/auth/refresh` at the start of every anonymous page load are expected (no
  refresh cookie yet) and were filtered out of the issue list after initially flagging them —
  matches the documented intentional behavior, not the Session-4 deadlock bug (already fixed).
