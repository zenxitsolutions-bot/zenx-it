## Done today

User asked for: recurring auto-scheduling of calls (e.g. "daily"), a preferred-time option, and
in-app pop-up reminders (their words: "similar to the way notifications appear on Facebook") a
configurable interval before the call. User explicitly framed this as a testing feature to refine
later based on usage, so scope was kept deliberately small — no telephony integration (the app has
none today, calls are appointment-scheduling only, same as before), no push notifications, no
message queue.

**Backend**
- `server/src/db/schema.sql` — `calls` table gets three new columns: `frequency`
  (`'once'|'daily'|'weekly'|'biweekly'|'monthly'`, default `'once'`), `reminder_minutes_before`
  (nullable int), `recurrence_parent_id` (nullable self-FK, display-only lineage).
- `server/src/db/migrate.js` — `schema.sql` is all `CREATE TABLE IF NOT EXISTS`, which never alters
  an existing table, so added a small set of `ALTER TABLE` statements (run after the schema apply,
  each wrapped to swallow a "duplicate column/key" error) so the migration stays idempotent and
  works against the dev database that already had the old `calls` table. Verified by running it
  twice.
- `server/src/jobs/callScheduler.js` (new) — the actual "auto-scheduling" mechanism. A 60s
  `setInterval` finds calls still `status: 'scheduled'` with `frequency != 'once'` whose
  `scheduled_at` has passed, inserts the next occurrence (same client/dietitian/notes/frequency/
  reminder, `scheduled_at` advanced by the frequency's interval — same time-of-day, which is what
  makes "preferred time" work with no separate field), and flips the *original* row's `frequency`
  back to `'once'` so the same tick logic never re-picks it up. A call that gets cancelled before
  its time never matches the query (`status` isn't `'scheduled'`), which is what stops a series —
  no separate "cancel the whole series" logic needed.
- `server/src/models/Call.js` — `frequency`/`reminderMinutesBefore`/`recurrenceParentId` added to
  `mapCall`, `CALL_COLUMNS` (so `updateCallById` can patch them), and `createCall`. New
  `listDueRecurringCalls()` for the scheduler.
- `server/src/schemas/call.schema.js` — `frequency` and `reminderMinutesBefore` added to both
  `createCallSchema` and `updateCallSchema`.
- `server/src/controllers/call.controller.js` — `createCall` passes the two new fields through;
  a client's own `PATCH` is now also allowed to send `reminderMinutesBefore` (not just
  `scheduledAt`/`status`) so they can change their own reminder preference without a dietitian —
  `frequency` stays out of that allowlist, so a client can only set recurrence at booking time, not
  edit it after (kept deliberately narrow for a testing feature).
- `server.js` — starts the scheduler after `connectDb()`.

**Frontend**
- `client/src/lib/callScheduling.js` (new) — shared constants/helpers: frequency options, reminder
  options, and the string-value ↔ API-value conversions (react-hook-form fields are strings; the
  API wants a number or `null`).
- `client/src/components/portal/shared/CallScheduleFields.jsx` (new) — the "Repeat" + "Remind me"
  selects, used by both booking dialogs. Split out specifically to keep both dialog files under
  CLAUDE.md's ~150-line component limit once the new fields were added.
- `client/src/components/portal/dietitian/ClientField.jsx` (new) — the dietitian dialog's "Client"
  picker, split out for the same line-count reason.
- `client/src/components/portal/client/CallFormDialog.jsx` and
  `.../dietitian/DietitianCallFormDialog.jsx` — booking form (not the reschedule form) now has
  Repeat and Remind me selects; submits `frequency`/`reminderMinutesBefore` to the API.
- `client/src/hooks/useCallReminders.js` (new) — polls the caller's own calls every 20s
  (`refetchInterval`, separate query key from the main `useCalls()` so this doesn't change existing
  screens' refetch behavior) and fires a Sonner toast once a call enters its reminder window.
  Already-shown call ids are tracked in `sessionStorage` so a remount doesn't re-fire the same
  toast within the tab's lifetime.
- `client/src/layouts/PortalLayout.jsx` — mounts `useCallReminders`, gated to `client`/`dietitian`
  roles only (admin's `useCalls()`/`GET /calls` is intentionally unscoped — *every* call on the

- `docs/API.md` — Calls section updated with the new fields and a "Known gaps" entry spelling out
  exactly what this feature is and isn't (no queue/lock, no push notification, no real calling).

## Decisions made

- No separate "preferred time" field — the existing `scheduledAt` datetime-local input's
  time-of-day *is* the preferred time, since each auto-generated occurrence keeps the same
  time-of-day and only advances the date.
  — Why: the user's own description ("choose a specific time... scheduled automatically for that
    time") is exactly what "keep the time, advance the date" already does; a second field would
    have meant reconciling two sources of truth for the same concept.
  — What it rules out: a cron-like "6:00 PM daily" scheduling model independent of a concrete first
    occurrence — ruled out as unnecessary complexity for a testing feature.
- Recurrence generation is lazy/rolling (one occurrence created per tick, off the previous one
  reaching its time), not upfront (e.g. generating the next 30 days at booking time).
  — Why: upfront generation of a call that is *itself* recurring would need to immediately decide
    whether to also pre-generate rules for it, which either spirals or needs an arbitrary cutoff;
    rolling generation is self-limiting by construction (cancel one occurrence, the chain stops) and
    needed no extra "is this series still active" bookkeeping.
- In-app toast (Sonner) polling client-side, not a push notification / service worker / browser
  Notification API.
  — Why: the user asked for "pop-up... similar to Facebook" and explicitly scoped this as a testing
    feature to refine later — an in-app toast satisfies the visible ask with the stack already in
    place (`sonner` was already a dependency, used everywhere else in the app), while a real push
    channel would need a backend delivery mechanism (web-push subscriptions, VAPID keys) that's a
    separate feature in its own right, not implied by "keep this as testing for now."
  — What it rules out: reminders firing when the tab isn't open. Flagged in `docs/API.md`'s known
    gaps, not silently decided.
- `server/src/jobs/callScheduler.js` is a bare `setInterval` in the same process, no job
  queue/lock.
  — Why: this app runs one server instance (confirmed by `render.yaml`/deploy docs); a queue would
    be solving a multi-instance race condition that doesn't exist yet. Flagged in known gaps so
    it's revisited if/when the app scales to multiple instances.

### Problems hit & how they were solved

- **CDP-driven mouse clicks (`computer` tool, both raw coordinates and element refs) silently did
  nothing on this page** — no navigation, no dialog opening, no console errors, even though the
  tool reported each click as successful. Root cause found via `document.visibilityState` /
  `document.hidden`: the automation tab reports **`hidden`** even while it has focus. Real clicks
  apparently don't get delivered to a page the browser itself considers backgrounded. Worked around
  by dispatching real DOM events via `javascript_tool` instead (`element.click()` for buttons/Radix
  Select triggers/options — since these are real `<button>`s, `.click()` fires a genuine `click`
  event that React's delegated listener picks up), and by using `navigate` directly instead of
  clicking sidebar links. Worth remembering for any future Claude-in-Chrome session on this
  project: if clicks silently no-op, check `document.visibilityState` before assuming the click
  coordinates are wrong.
- **Same root cause also silently defeated `useCallReminders`'s live 20s poll**: TanStack Query's
  `refetchInterval` does not run while `document.visibilityState === 'hidden'`
  (`refetchIntervalInBackground` defaults to `false` in this codebase's react-query version) — so
  after the first (invalidation-driven) reminder toast, `read_network_requests` showed zero further
  `/api/calls` polling for a full minute of real wall-clock waiting, even though the booked call was
  still well inside its reminder window the whole time. This is *not a bug in the feature* — a real
  user's minimized/backgrounded tab would behave identically, which is a legitimate, if minor,
  known gap for a testing-stage in-app-only reminder (see `docs/API.md`). Confirmed the mechanism
  itself is sound (the first toast did fire, for real, from real UI interaction) rather than
  chasing a second visual toast the framework was correctly declining to show.
- Left the booked test call in place afterward (real upcoming call, `client@nourishly.test`,
  currently `Daily`/10-minute-reminder) rather than deleting it — it's a real live demo of the
  feature in the seeded account and the scheduler will keep rolling it forward daily as long as the
  dev server runs; flagged here in case a future session wants to clean it up.
