# Work log — 2026-08-27

**Phase:** Multi-tenancy (shared ZenX auth → real org isolation)
**Session time:** 2026-08-27

## Done today

Ask (from the ZenX side of this project): implement shared authentication between ZenX
(admin/subscription management) and this app (the customer SaaS), organization/tenant
architecture, RBAC, and "each customer can only access their own organization's users and data" —
without rebuilding either app.

Investigated first rather than assuming greenfield: admin-server already has a complete,
previously-built shared-auth backbone (dual JWT realms, `companies`/`users`/`applications`/
`application_access` tables, `provisionCustomerAccount`, `issueHandoffToken`), and this app already
**receives** that handoff (`auth.controller.js#handoff`, `users.zenx_user_id`) — proven end-to-end
before today per that code's own comments. The actual gap: this app had **zero tenant scoping** —
no `company_id` anywhere, `admin` was platform-global, and `handoff` discarded the token's own
`company_id`/`role` claims, hardcoding every incoming ZenX company contact to `'dietitian'`. That's
what today's work closes. Plan written and approved (plan mode) before coding; two product
decisions confirmed with the user first: pre-existing data backfills onto one real, explicit
"Legacy Practice" company (not left NULL), and `program_plans` becomes per-company, not shared.

### What was built

- **Schema** (`server/src/db/schema.sql`, `db/migrate.js`): `company_id` added to the three
  top-level owner tables — `users` (+ `company_slug`), `enquiries`, `program_plans`. Every other
  tenant-owned table (`recipes`, `plans`, `calls`, `consultation_schedules`, `messages`,
  `client_notes`, `progress`, `reports`, `dietitian_weekly_hours`,
  `dietitian_availability_exceptions`, `email_log`, ...) already FKs to a `users` row and is scoped
  transitively through that user's `company_id` — no schema change needed there, same pattern this
  codebase already uses for child tables (`plan_meals` via `plan_id`, `recipe_tags` via
  `recipe_id`). `migrate.js` backfills existing rows from a new `LEGACY_COMPANY_ID` env var and
  fails fast (not silently) if it's unset and there's data to backfill.
- **admin-server** (sibling repo) gained `seedLegacyCompany()` in its own `seed.js` — creates one
  real `companies` row + customer `users` row + `zenx-dietitian` `application_access` grant, same
  idempotent pattern as its existing seeds, so this app's grandfathered data points at a real,
  ZenX-managed tenant rather than an invented local id.
- **`auth.controller.js#handoff`**: now reads `payload.company_id`/`company_slug`/`role` instead of
  discarding them. Maps ZenX's `'wellness_admin'` grant role → this app's local `'admin'` (the org
  admin who can create/manage their own org's dietitians/clients); anything else falls back to
  `'dietitian'` (prior hardcoded behavior). `models/User.js#createUser` now requires `companyId`.
- **The actual RBAC fix — `admin` went from platform-global to org-scoped everywhere.** Every
  list/find touched to require and filter by `companyId` (`User.js`, `Enquiry.js`, `ProgramPlan.js`
  directly; `Recipe.js`/`Plan.js`/`Call.js`/`Report.js`/`EmailLog.js` via a join through their
  owning user's company). The single highest-leverage fix: `utils/scope.js#assertDietitianOwnsClient`
  — reused across notes/messages/progress/consultation-schedule controllers — used to be a total
  no-op for `admin`; it now company-checks (404) for every role first, so extending it fixed all of
  those call sites at once instead of one by one. New `assertUserInCompany` for the remaining bare
  by-id lookups (reports, recipes, plans, calls, program plans, client notes, email log — each
  reached by a wrong-company id now 404s, not 403, so existence isn't revealed).
- Cross-org creation guards: `user.controller.js#createUser` always stamps
  `companyId: req.user.companyId` (never client-supplied); `plan.controller.js`/`call.controller.js`
  now verify an admin-supplied client/dietitian pair are both real accounts in the admin's own org
  before pairing them, closing a same-tenant-but-wrong-pairing gap that existed even before today.
- Public, unauthenticated `enquiry.controller.js#createEnquiry` now always attaches to
  `env.legacyCompanyId` — there's one public funnel today; a real per-company one (resolved from a
  URL slug) is explicitly out of scope for this pass, noted inline.
- Fixed two pre-existing test/tooling call sites that would otherwise break against the new
  `NOT NULL`-on-fresh-install `company_id`: `tests/integration/availability.race.test.js`'s raw
  `INSERT INTO users`, and the historical `migrate-from-mongo.mjs`.
- New `tests/integration/multiTenant.isolation.test.js` — two companies, same shape (admin +
  dietitian + client each), asserts `listUsers`/`countUsers`/`listRecipes`/`listEnquiries` never
  cross company boundaries, and that both `assertUserInCompany` and (crucially) the now-fixed
  `assertDietitianOwnsClient` reject a cross-company id for an `admin` caller, not just a
  `dietitian`.

### Problems hit & how they were solved

- The real risk in a sweep like this isn't the obvious list endpoints — it's the bare
  `findXById(req.params.id)` lookups scattered through update/delete/get-file handlers that had no
  ownership check at all for `admin` (correct in the old single-tenant world, a real cross-org leak
  in this one). Went through every controller's `role === 'admin'`/`role !== 'admin'` branches
  explicitly (grepped for them) rather than trusting the list-endpoint fixes alone to be enough —
  found and fixed several (client notes, progress, plans, calls, availability's dietitian resolver,
  email log) that the "just scope the list queries" pass would have missed.
- `email_log`'s `related_entity` is polymorphic (client/appointment/enquiry, no FK) — company can't
  be read off one join. Resolved per-row by joining each possible target to its own company
  (client → its own `company_id`; appointment → its dietitian's; enquiry → its own), and excluding a
  row with no related entity from a company-scoped list rather than showing it platform-wide
  (there's none in practice today — every `sendEmail()` call site sets one — but this fails closed
  if that ever changes).
- `services/consultationScheduleService.js#cancelFutureGeneratedCalls` called the now-`companyId`-
  required `listCalls` with no company in scope at all — an internal service function, not an HTTP
  handler. Threaded `companyId` through its signature (the caller already has the client's
  `companyId` in scope) rather than relaxing the model's requirement, to keep the "every HTTP path
  is forced to consciously scope" guarantee intact.
- Not verified against a live database this session (no local MySQL reachable, consistent with
  several recent sessions per this worklog) — `node --check` on every new/touched file, and a full
  read-through of every touched controller's route-level `authorize()` gates against the
  assumptions the controller-level fixes made (recipe/plan/call/programPlan/consultationSchedule/
  insights/emailLog routers) to catch a role-gating mismatch without a running server.

### Decisions made

- Company scoping via one `company_id` column on the three top-level owner tables + transitive
  joins through the owning user, not a denormalized `company_id` on all ~17 tables — smaller
  migration, no second copy of tenant identity to keep in sync, same convention this codebase
  already uses for other child tables.
- Pre-existing data backfills onto one real, ZenX-managed "Legacy Practice" company (confirmed with
  the user) rather than staying `NULL` — no NULL-handling branch needed anywhere in the new scoping
  code.
- `program_plans` is per-company (confirmed with the user) — each org curates its own, not a
  platform-shared catalog.
- The public enquiry funnel stays single-company (`LEGACY_COMPANY_ID`) for now; a real per-company
  public funnel is explicitly future work, not silently half-built here.
