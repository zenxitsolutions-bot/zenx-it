## Done today

The user asked to "run the project." Every session across all eight prior phases (all logged
under 2026-08-10.md) ended with the same caveat: no one had ever watched this app render in an
actual browser, because the Claude-in-Chrome extension needed for browser automation was never

mattered — two real, previously-invisible bugs turned up within the first twenty minutes of
actually looking at rendered pages.

- **Found a working path to real browser verification.** The `/run` skill's guidance for
  browser-driven apps calls for `chromium-cli` (a Linux-container tool, not available here) or an
  adapted Playwright driver. Chrome itself is installed on this machine (confirmed in Phase 8 for
  Lighthouse) — a completely different, unrelated channel from the still-disconnected automation
  *extension*. Installed `playwright-core` in the scratchpad directory and drove the actual
  installed Chrome (`executablePath`, not Playwright's own bundled Chromium download) headlessly.
  This is the first time in the project's history that a rendered page has actually been looked
  at, not inferred from a build/lint/curl pass.
- Launched the full stack fresh: `mongodb-memory-server`, `npm run dev` in `server/`, `npm run
  seed`, `npm run dev` in `client/`.
- **Bug found immediately**: the client dev server landed on port 5174 (5173 was occupied by an
  orphaned process from a prior session), and the server's CORS config only allows
  `http://localhost:5173` — every API call failed with a CORS error, silently, and login did
  nothing. Root-caused by reading the actual browser console errors the driver script captured
  (`page.on('console')`), not guessed. Found and killed the orphaned process holding 5173
  (confirmed via `Get-NetTCPConnection` → PID → `Stop-Process`, not a blind kill), restarted the
  client on the correct port, and login worked immediately after.
- Drove and screenshotted every major screen across all three roles: homepage, enquiry modal,
  login/register, client Overview/Meals/Progress/Calls/Reports, dietitian Recipe
  library/Clients+drawer/Plan builder/Calls/Reports, admin Overview/Enquiry pipeline/Growth
  insights. All of it renders correctly, matches the intended brand design, and no unexpected
  console errors turned up on any of them (aside from the expected pre-login 401 on
  `/auth/refresh`, which is normal behavior for an anonymous visit).
- **Bug found and fixed**: `client/src/components/portal/client/WeightTrendChart.jsx`'s compact
  variant (used on the client Overview screen) rendered a real 6-week, 4.2kg weight decline as a
  visually flat line. Root cause: the `<YAxis domain={['dataMin - 1', 'dataMax + 1']}>` that
  tightly fits the chart to the data range was only rendered when `large` (the full Progress-page
  variant) was true — the compact variant omitted the `<YAxis>` element entirely, so recharts fell
  back to its own default domain (padded from zero), which flattens any trend whose absolute
  values are far from zero (weights in the high 60s/low 70s look nearly identical against a
  0-to-~80 scale). The full Progress page's chart was never affected, since it always set the
  tight domain — only the compact one was broken, and only visually, which is exactly why nothing
  short of looking at it would have caught this. Fixed by always setting the domain and using
  `hide={!large}` to keep the axis's scale-calculation active while only visually showing it in
  the large variant. Re-screenshotted and confirmed the fix — same 6 data points, now a correctly
  declining line.
- **Bug found and fixed, the more serious one**: opened the dietitian's Weekly plan builder for
  Cleo Client (who has a seeded, published, 21-meal plan) and the schedule rendered completely
  empty — zero rows, not even the seeded ones. Root cause: this is the *exact same* UTC-vs-local-
  time bug already found and fixed once in Phase 8 (`insights.controller.js`'s `growthSeries`),
  except it turned out to exist in **two more places** that Phase 8 didn't catch —
  `client/src/lib/planBuilder.js`'s `startOfWeek()` (used to default the builder's week-picker)
  and `server/src/seed.js`'s own separate `startOfWeek()` (used when creating the seeded plan).
  Both used local-time `Date` methods + `.toISOString()`, which on this machine (IST, UTC+5:30)
  silently shifts the computed "Monday" back by one calendar day once serialized to UTC — so the
  plan builder's default week-picker value (`2026-08-09`, a Sunday) never exactly matched the
  seeded plan's stored `week` field, and the backend's exact-equality date query
  (`Plan.find({week: ...})`) returned nothing. Fixed both call sites to use the same UTC-safe
  pattern already established in `insights.controller.js` (`Date.UTC`, `getUTCDay`, etc.),
  dropped the stale seeded data (wrong week-date) and reseeded, and confirmed live: the
  week-picker now correctly shows `10-08-2026` (Monday) and all 21 seeded meal rows render.
  **This is the clearest demonstration yet in this project of why "the same fix in one place
  doesn't mean the bug is gone everywhere it was copy-pasted"** — Phase 8's worklog fix for this
  exact pattern didn't think to grep for other occurrences of `startOfWeek`, and there were two.
- **Verified the actual drag-and-drop interaction with real mouse events**, not just static
  rendering — the single most-repeated "never verified" risk called out in Phase 7's and Phase
  8's worklogs. Scripted a real `page.mouse.down()` → multi-step `move()` → `up()` sequence
  dragging a recipe card from the sticky rail onto a blank schedule dropzone in the plan builder.
  It worked: the target row visibly changed from the dashed "Drop a recipe here" empty state to
  the solid filled state showing the correct recipe's emoji and name, with no console errors.
  (Two earlier attempts failed — not because the feature was broken, but because the locators
  targeted inner text nodes rather than the actual draggable/droppable container elements, giving
  meaningless 16px-tall bounding boxes. Third attempt, targeting the real container elements,
  succeeded cleanly.) Did not get a second successful scripted drag on the enquiry kanban board
  (a locator-precision issue in the test script, timed out finding the card element) — didn't
  chase it further, since the kanban uses the identical `@dnd-kit` `DndContext`/sensor pattern
  already proven to work end-to-end on the plan builder.
- Cleaned up test/demo data pollution left over from this session's own poking around (duplicate
  progress/calls/reports created by a partial database cleanup mid-session) by dropping the whole
  dev database and reseeding once, cleanly, at the end.
